# Developer Log (DevLog): Swapchain, Image Views \& Dynamic Rendering Pivot

**Date:** October 29, 2026

**Project:** Vulkan 3D Rendering Engine (`RenderingEngine`)

**Target Environment:** Windows 11 (x64), Visual Studio 2026 (MSVC v19.51), C++20

## 1\. Summary \& Architecture Overview

Today’s objective was to complete the foundational Vulkan setup phase by establishing the Logical Device, Swapchain, and Image Views. A major architectural pivot was made during this session: bypassing the legacy `vk::RenderPass` and `vk::Framebuffer` objects entirely in favor of **Vulkan 1.3 Dynamic Rendering**.

Additionally, the project structure was refactored to introduce a clean boundary between Core Engine systems (Instance, Device, Window) and a newly created `Renderer/` module, which will handle shaders, pipelines, and command recording.

### Core Systems Implemented:

* **Logical Device \& Queues:** Initialized `vk::raii::Device` and successfully extracted the Graphics and Presentation queue handles.
* **Swapchain Setup:** Configured `vk::raii::SwapchainKHR` matching the monitor's capabilities, selecting optimal surface formats and presentation modes.
* **Image Views:** Retrieved raw swapchain images and wrapped them in `vk::raii::ImageView` to allow the GPU to interpret them as 2D color targets.
* **Dynamic Rendering Pivot:** Enabled `dynamicRendering` feature on the physical device to permanently eliminate RenderPass/Framebuffer boilerplate.

## 2\. Dev Log Details \& Architectural Decisions

* **GPU Selection Strictness:** Opted for a discrete-first hardware selection strategy. Laptops with hybrid graphics (NVIDIA Optimus) naturally default to the Integrated GPU (Intel Iris Xe). The engine now strictly searches for a Discrete GPU (RTX 3050) first and only falls back to Integrated if absolutely necessary.
* **Renderer Segregation:** To prevent `Engine.cpp` from becoming a monolithic god-class, rendering logic is being moved into a dedicated `Renderer` folder containing `Pipeline`, `CommandBuffer`, and `Shaders`.

## 3\. Issues Encountered \& Solutions Applied

### Issue 1: Integrated GPU Defaulting

* **Error:** Log showed `Selected Device: Intel(R) Iris(R) Xe Graphics` despite an RTX 3050 being present.
* **Cause:** The `enumeratePhysicalDevices()` loop picked the first GPU that satisfied the minimum extensions and queue requirements, which was the iGPU.
* **Solution:** Added explicit priority logic using a `hasDGPU` flag to check if `deviceType == vk::PhysicalDeviceType::eDiscreteGpu`.

### Issue 2: Strict Const-Correctness \& Iterator Errors (Technical Debt Logged)

* **Error:** Attempting to refactor the GPU selection loop without the `hasDGPU` flag resulted in a cascade of C++20 compiler errors: `C2664` (cannot convert argument from `const\_Ty` to `vk::raii::PhysicalDevice \&`) and `C2088` (built-in operator `!` cannot be applied).
* **Cause:** `vk::raii::PhysicalDevice` handles enforce incredibly strict `const` qualifiers and have deleted assignment operators. Standard C++ loop captures and null checks conflict heavily with these RAII bindings if not perfectly cast.
* **Solution (Workaround):** Reverted to the manual `hasDGPU` boolean flag approach.
* **Technical Debt:** The `hasDGPU` flag is officially marked as a known workaround. It successfully forces the Discrete GPU selection for now, but will be refactored in the future to more elegantly store the optimal device handle without triggering Vulkan-HPP compilation fits.

### Issue 3: Vulkan-HPP Type Mismatch on Image Views

* **Error:** `E0304: no instance of overloaded function "vk::ImageViewCreateInfo::setSubresourceRange" matches the argument list`
* **Cause:** Attempted to pass raw integers `(vk::ImageAspectFlagBits::eColor, 0, 1, 0, 1)` directly into `setSubresourceRange()`. Vulkan-HPP strictly requires its own wrapper structs.
* **Solution:** Instantiated a proper `vk::ImageSubresourceRange` object using the method chaining builder pattern (`.setAspectMask(...).setBaseMipLevel(...)`) and passed it into the function.
