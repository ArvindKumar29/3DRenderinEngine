# Developer Log (DevLog): Vulkan Initialization & Physical Device Selection

**Date:** October 28, 2026  
**Project:** Vulkan 3D Rendering Engine (`RenderingEngine`)  
**Target Environment:** Windows 11 (x64), Visual Studio 2026 (MSVC v19.51), C++20

---

## 1. Summary & Architecture Overview

Today’s objective was to establish the foundational Vulkan objects using the C++ RAII bindings (`vulkan_raii.hpp`) and integrate them with a GLFW window system. The core focus was on maintaining a clean, modular architecture (Single Responsibility Principle) by avoiding a monolithic `Engine.cpp` and explicitly segregating windowing, instance creation, and physical device evaluation.

### Core Systems Implemented:
* **Validation Layers:** Configured standard validation layers (`VK_LAYER_KHRONOS_validation`) for debugging and safety.
* **Vulkan Instance (`vk::raii::Instance`):** Initialized the Vulkan API context and linked it with required GLFW instance extensions.
* **Window & Surface (`Window` Class):** Setup GLFW (with `GLFW_NO_API`) and abstracted the OS-specific window into a Vulkan-compatible `vk::raii::SurfaceKHR`.
* **Physical Device Selection (`Device` Class):** Built a robust evaluation pipeline to iterate through available GPUs (`vk::raii::PhysicalDevice`) and score them based on API version (1.3), Queue Family support (Graphics & Present), and required device extensions (Swapchain).

---

## 2. Dev Log Details & Architectural Decisions

* **Dependency Injection over Static State:** Decided against using static variables or circular includes to share the `Surface` with the `Device`. Instead, the `Engine` acts as an orchestrator, retrieving the `Surface` pointer from the `Window` class and injecting it into `Device::getPhysicalDevice(...)` by reference.
* **Instance vs. Device Extensions:** Clarified the strict boundary between extensions required to talk to the OS (Instance extensions like `VK_KHR_surface` provided by GLFW) and extensions required to talk to the GPU hardware (Device extensions like `VK_KHR_swapchain`).

## 3. Issues Encountered & Solutions Applied

The transition to C++20 and `vulkan.hpp` RAII semantics introduced several strict compile-time errors. 

### Issue 1: C++20 Designated Initializer Rejection
* **Error:** `E2357: a designator cannot be used with a non-aggregate type "vk::ApplicationInfo"`
* **Cause:** Attempted to use C-style designated initializers (`.pApplicationName = ...`) on `vk::` structures. The Vulkan C++ wrapper structures contain custom constructors, rendering them non-aggregate types in C++20.
* **Solution:** Refactored initialization to utilize `vulkan.hpp`'s built-in method chaining pattern (e.g., `vk::ApplicationInfo().setPApplicationName(...)`).

### Issue 2: Deleted Copy Constructor (RAII Double-Free Prevention)
* **Error:** `E1776: function "vk::raii::Context::Context(const vk::raii::Context &)" cannot be referenced -- it is a deleted function`
* **Cause:** Passed `vk::raii::Context` into a function *by value*. Vulkan RAII objects delete their copy constructors (`= delete`) to prevent underlying C-level Vulkan handles from being destroyed when a copied object goes out of scope.
* **Solution:** Enforced strictly passing all Vulkan RAII objects (`Context`, `Instance`, `PhysicalDevice`) by reference or constant reference (e.g., `const vk::raii::Context& ctx`).

### Issue 3: Missing CMake Presets in Visual Studio Toolbar
* **Error:** Missing `VS 2026 + vcpkg` option in the target dropdown; missing `vulkan_raii.hpp` header.
* **Cause:** Visual Studio latched onto residual, manually created `.sln` and `.vcxproj` files in the project root instead of generating the native CMake cache via `CMakePresets.json`.
* **Solution:** Deleted root `.sln`/`.vcxproj`/`.vs` files. Switched to CMake Folder View, generated the cache targeting the `debug` preset, and selected `app.exe` as the startup item.

### Issue 4: Circular Dependency in Headers
* **Error:** `C3646: 'device': unknown override specifier` and `missing type specifier - int assumed` in `Engine.h`.
* **Cause:** `#include "Engine.h"` was accidentally placed inside `Device.h`, causing an infinite compiler inclusion loop where the `Device` class was referenced before it was defined.
* **Solution:** Removed the `Engine.h` include from `Device` files, ensuring `Device` remains completely decoupled from the application orchestrator.

### Issue 5: Lambda Predicate Returning Void
* **Error:** `E0304: no instance of overloaded function "std::ranges::_All_of_fn::operator()" matches the argument list`
* **Cause:** Missing `return` statement inside the outer `std::ranges::all_of` lambda in the physical device extension checker. Furthermore, extension vectors were being captured by value, causing unnecessary memory copying.
* **Solution:** Added the `return` keyword before `std::ranges::any_of` and updated the lambda capture list to pass outer variables by reference (`[&]`).

### Issue 6: GPU Detection Failure (Mixing Extension Types)
* **Error:** Runtime Exception: `No GPUs with vulkan support found on system!!!`
* **Cause:** The `Device` selection algorithm failed all available GPUs because `glfwGetRequiredInstanceExtensions()` was passed as the required *Device* extensions. GPUs do not support OS-level instance extensions natively.
* **Solution:** Created a distinct `deviceExtensions` vector containing only required hardware features, stripping GLFW dependencies from the GPU querying logic.

### Issue 7: Explicit Constructor Conflict for Macros
* **Error:** `E2334: copy-list-initialization cannot use a constructor marked 'explicit'`
* **Cause:** Initializing a `std::vector<const char*>` with `{ VK_KHR_swapchain }`. Since `VK_KHR_swapchain` is defined as the integer `1` in Vulkan headers, the compiler attempted to call the `std::vector`'s explicit size constructor instead of inserting a string.
* **Solution:** Switched the macro to `VK_KHR_SWAPCHAIN_EXTENSION_NAME`, which correctly resolves to the string literal `"VK_KHR_swapchain"`.
