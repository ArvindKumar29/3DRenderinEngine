# Devlog: Vulkan Facade Refactor, RAII Teardown Fix & Custom Vertex/Index Buffers

**Date:** October 31, 2026

**Milestone:** Milestone 1.5 / Milestone 2 Foundation (Geometry Pipeline)

**Hardware:** NVIDIA GeForce RTX 3050 Laptop GPU | Windows 11 (x64)

## 1. Overview & Objectives

After getting the first hardcoded triangle on screen using Vulkan 1.3 Dynamic Rendering and Synchronization2, today's session focused on three major engineering goals:

1. **Architectural Decoupling (Facade Pattern):** Cleaning up `Engine.h` and `Engine.cpp` by moving all low-level Vulkan classes (`Instance`, `ValidationLayers`, `Window`, `Device`, `Pipeline`, and `CommandPool`) behind a single backend controller (`Vulkan/vlk.h` & `vlk.cpp`).

2. **Fixing the Window-Close RAII Crash:** Diagnosing and resolving an assertion failure inside `vk::raii::SurfaceKHR::~SurfaceKHR()` when closing the application window.

3. **Hardware Vertex & Index Buffers:** Removing hardcoded vertex arrays from `main.vert` and feeding custom `Vertex` (`pos` + `color`) and index (`uint32_t`) data from C++ into GPU memory to render an indexed RGB Quad.

## 2. Architectural Refactor: The `vlk` Backend Facade

Previously, `Engine` directly held and managed every low-level Vulkan handle. To keep `Engine` clean for high-level rendering systems (meshes, camera, materials, lighting), the codebase was reorganized:

```
src/engine/
├── Engine.h / Engine.cpp          # High-level engine entry (talks ONLY to vlk)
├── Vulkan/                        # Low-level Vulkan 1.3 Backend
│   ├── vlk.h / vlk.cpp            # Master Vulkan Facade / Orchestrator
│   ├── Window.h / .cpp            # GLFW Window, SurfaceKHR, Swapchain, ImageViews, Sync2 Barriers
│   ├── Instance.h / .cpp          # vk::raii::Instance setup
│   ├── ValidationLayers.h / .cpp  # Khronos validation layer checks
│   ├── Device.h / .cpp            # PhysicalDevice (dGPU selection) & LogicalDevice (1.3 pNext chain)
│   ├── Pipeline.h / .cpp          # SPIR-V loader, Vertex Input state, Dynamic Rendering Pipeline
│   └── CommandPool.h / .cpp       # CommandPool, CommandBuffer & draw call recording
└── Renderer/                      # High-level Geometry & Scene Data
    ├── Vertex.h                   # Vertex structure, Binding & Attribute Descriptions
    └── Buffers.h                  # VertexBuffer & IndexBuffer GPU memory management

```

Now, `Engine::run()` simply delegates backend initialization and the frame loop to `vulkanContext.run()`, cleanly separating API boilerplate from engine features.

## 3. Bug Fix: `vk::raii::SurfaceKHR` Shutdown Crash

### The Symptom

Closing the GLFW window triggered a debug break (`abort()`) inside `vulkan_raii.hpp` at `vk::raii::SurfaceKHR::getDispatcher()`:

```
VULKAN_HPP_ASSERT( m_dispatcher->getVkHeaderVersion() == VK_HEADER_VERSION );

```

### Root Cause

In `vlk::~vlk()`, `vulkanInstance.instance = nullptr;` was explicitly called to destroy the Vulkan instance before `glfwDestroyWindow()`. However, `window.surface` (`vk::raii::SurfaceKHR`) was **not** cleared before destroying the instance, and an extra copy of `vk::raii::PhysicalDevice pd` was still alive.

When `vlk::~vlk()` finished executing its body and C++ began running member destructors (`Window::~Window()`), `window.surface` attempted to call `vkDestroySurfaceKHR` using the `m_dispatcher` pointer of an already-destroyed `vk::raii::Instance`—resulting in a dangling pointer dereference.

### The Fix

Explicitly destroying `window.surface` and `pd` **before** `vulkanInstance.instance = nullptr;` inside `vlk::~vlk()` resolved the issue completely:

```
device.graphicsQueue = nullptr;
device.logicalDevice = nullptr;
device.physicalDevice = nullptr;
pd = nullptr;

window.surface = nullptr;          // Destroy surface while Instance is still alive!
vulkanInstance.instance = nullptr; // Now safe to destroy Instance

```

The application now exits cleanly with code `0 (0x0)`.

## 4. Implementing Vertex & Index Buffers

### Step 1: `Vertex` Struct, Binding & Attribute Descriptions (`Vertex.h`)

Replaced the hardcoded shader arrays with a C++ `Vertex` struct containing `glm::vec3 pos` and `glm::vec3 color` ($24\text{ bytes}$ stride). Implemented the two static pipeline layout helpers:

* **`getBindingDescription()`:** Configured binding `0` with `sizeof(Vertex)` stride and `vk::VertexInputRate::eVertex`.

* **`getAttributeDescription()`:** Returned a `std::array<vk::VertexInputAttributeDescription, 2>` mapping `pos` (`location = 0`, `offsetof(Vertex, pos)`) and `color` (`location = 1`, `offsetof(Vertex, color)`) using `vk::Format::eR32G32B32Sfloat`.

### Step 2: GPU Buffer Allocation & Memory Mapping (`Buffers.h`)

Created `vertexBuffer` and `indexBuffer` structures managing both `vk::raii::Buffer` and `vk::raii::DeviceMemory`:

1. Queried buffer memory requirements via `buffer.getMemoryRequirements()`.

2. Bitmask-matched physical device memory types supporting `eHostVisible | eHostCoherent`.

3. Allocated `memReq.size` bytes on the GPU, bound the memory to the buffer handle, and uploaded CPU vector data via `mapMemory()`, `memcpy()`, and `unmapMemory()`.

4. Added an **Index Buffer** (`vk::BufferUsageFlagBits::eIndexBuffer`) to reuse 4 unique vertices across 6 indices (`uint32_t`) and render a complete RGB Quad via `cmdBuffer.bindIndexBuffer(...)` and `cmdBuffer.drawIndexed(...)`.

## 5. Debugging Log: Mistakes & Lessons Learned

During the Vertex Buffer integration, several classic Vulkan/C++ bugs came up and were fixed:

1. **RAII Local Variable Lifetime Trap:**

   Initially, `vk::raii::DeviceMemory` was declared as a local variable inside `createVertexBuffer()`, and `createVertexBuffer()` was called inside `recordCommandBuffer()`. Because `vk::raii` handles free GPU resources as soon as they go out of scope, the memory was being freed before the GPU could even execute the draw call. Moving both `buffer` and `bufferMemory` to persistent struct members and initializing them once in `vlk::init()` fixed the lifetime issue.

2. **Byte Size vs. Vertex Count in `draw()`:**

   Passing `bufferSize` ($72\text{ bytes}$) instead of `VB.size()` ($3\text{ vertices}$) to `cmdBuffer.draw()` told the GPU to read 72 vertices instead of 3.

3. **The Black Right-Angle Triangle Bug (Attribute Overwrite):**

   On the first successful run with vertex buffers, the screen showed a pitch-black triangle stretched between $(0,0)$, $(1,0)$, and $(0,1)$.

   * **Cause 1:** In `getAttributeDescription()`, `.setOffset(offsetof(Vertex, color))` was chained onto the same single `VertexInputAttributeDescription` right after `.setOffset(offsetof(Vertex, pos))`. This overwrote `location = 0` (`inPosition`) with the byte offset of `color` ($12\text{ bytes}$), so the shader was reading RGB color values `(1,0,0)` and `(0,1,0)` as screen coordinates while `location = 1` (`inColor`) defaulted to `(0,0,0)` black!

   * **Cause 2:** After switching to `std::array<vk::VertexInputAttributeDescription, 2>`, copy-pasting left `.setLocation(0)` on both `[0]` and `[1]`. Changing `inputAttributeDescription[1]` to `.setLocation(1)` immediately restored the full interpolated RGB colors.

## 6. Current Result & Next Steps

* **Result:** Rendering a smooth, color-interpolated 4-vertex, 6-index Quad via custom C++ Vertex and Index Buffers with zero validation errors and a clean `0x0` shutdown.
